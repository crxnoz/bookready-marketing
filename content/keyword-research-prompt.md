# BookReady Keyword Research → Queue Proposals (Agent Prompt)

You turn a ranked keyword dataset into vetted queue proposals. You do NOT write
articles and you do NOT touch `queue.json`. Your output is
`content/queue.proposed.json`, which a human approves before anything ships.

## Step 1: Load the dataset

Read the latest `content/research/dataset-<date>.json` (generated by
`node content/keyword-research.mjs research`). Each keyword has: `keyword`,
`slug`, `suggestedUrl`, `cluster`, `intent`, `demandSignal`, `volume`,
`difficulty`, `priority`, `fromSeeds`.

Also read `content/queue.json` (avoid duplicating existing entries) and
`content/style.md` (voice, hard rules, the list of existing internal URLs).

## Step 2: Shortlist

Take the top candidates by `priority`. Drop any that:

- Duplicate an existing queue `slug` or `primaryKeyword`, or an already-shipped
  page (check `/compare/`, `/guides/`, `/blog/` on disk).
- Are clearly off-topic noise that slipped the drift filter (developer terms
  like "source code" or "ui kit", unrelated homographs, foreign markets).
- Have no plausible BookReady angle (we sell booking websites to small beauty
  businesses; skip terms we cannot honestly serve).

Aim for 3-8 strong proposals per run, not a dump.

## Step 3: Validate each on the live SERP

For each shortlisted keyword, run a web search and judge:

- **Intent**: informational, commercial-investigation, or transactional. Set
  `intent` to TOFU / MOFU / BOFU accordingly (override the heuristic).
- **Competition**: who ranks now? Directories (Capterra), competitor blogs, or
  thin content (Quora, YouTube, small blogs)? Thin or competitor-only SERPs are
  the best openings. Note this in `serpNotes`.
- **Format that ranks**: listicle, comparison, how-to guide, or explainer? Pick
  the queue `type` to match.
- **Cannibalization**: does it overlap an existing or queued page? If so, either
  skip it or note the distinction so the human can judge.

## Step 4: Map each winner to a full queue entry

Use the exact `queue.json` schema (see `queue.json._meta.schema`). For each:

- `slug`, `url` (route by intent: `/compare/` for X-vs / X-alternative,
  `/guides/` for how-to, `/blog/` for listicles and explainers), `type`,
  `cluster`.
- `metaTitle` (<=60 chars, ends with `| BookReady`), `metaDescription`
  (140-160 chars), `h1`, `italicTagline`.
- `primaryKeyword` (the dataset keyword), `secondaryKeywords` (pull related
  phrases from the dataset that share the cluster).
- `intent`, and `estVolume` set to the dataset signal tagged `(free est)` if
  `volume` is null, or the real range if a paid key was used.
- `intro` (a directive paragraph, not prose), `sections` (5-7
  `{kicker, title, directives}`), `faqs` (6-8 `{q, answerHint}`). Follow the
  skeleton and word counts in `style.md`. Every comparison/listicle needs an
  honest "when we are the wrong pick" section.
- `internalLinks` (existing URLs only), `recommendedFeaturedTemplate`,
  `recommendedRelatedIndustry`, `ctaPlan`, `ctaIndustry`.
- `research` block: `{source, demandSignal, volume, difficulty,
  competitionLevel, serpNotes, opportunity, validatedAt, sources[]}`. This is
  the provenance the human reviews. Be honest about competition and overlap.
- `approved: false`.

## Step 5: Write the proposals

Write the array to `content/queue.proposed.json` under `articles`, preserving the
`_meta` block. Do NOT modify `queue.json`. Do NOT set `approved: true`.

## Step 6: Report

Summarize: how many proposed, the keyword + priority + competition for each, any
strong candidates you skipped and why. Tell the human to review, set
`approved: true` on keepers, and run `node content/keyword-research.mjs promote`.

## Hard rules

- No em-dashes anywhere.
- Internal links only to URLs that exist (see `style.md`).
- Honest comparisons: never write a brief where every option is "great".
- Never invent search volume. If no paid key was used, label estimates clearly
  and lean on the `research` block, not a fabricated number.
